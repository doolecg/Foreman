Kimi as a full replacement for Claude

Cancelled by Dayle on 5 November 2026. Nothing was built. Kept only as a record of the research. Do not build from this page without asking.

Status: plan only, nothing built. Branch: dev-4.4.0. Rewritten 5 November 2026 after you said Kimi must be able to replace Claude entirely, graph and sub-agents included. Research done the same day.

Read this first

  1. A setting picks the main agent: Claude (the default), Kimi, or OpenCode. When it is Kimi, Claude is not needed at all: chat, the Orchestration graph, sub-agents and the Model Engine kit all run on Kimi Code CLI.
  2. The research says this is possible. Kimi Code CLI has sub-agents, a rich set of hook events including SubagentStart and SubagentStop, a standard chat protocol (ACP), skills and project agent files, and, according to the research, an MIT licence that I still have to check myself.
  3. The hard part is inside Foreman, not Kimi. Today the chat view, the graph and the sub-agent list all read Claude's own events and files. They need to read one neutral event format, with one reader per agent.
  4. This is the largest feature on the list: a spike plus five phases (A to E), probably several sessions. You can stop after any phase and still have something that works.
  5. Section 7 has the decisions for you. I have picked a default for each.

1. What we know (research, 5 November 2026)

  • The tool. Kimi Code CLI, repo MoonshotAI/kimi-code, MIT licence (the research agent read the LICENSE file; I have not opened it myself), version 2.5.1. Install by script, Homebrew or npm install -g @moonshot-ai/kimi-code. The research says the older Python kimi-cli is archived (not checked by me).
  • Sign-in. /login inside kimi. Kimi keeps its own credentials in ~/.kimi-code. Foreman stores no key.
  • Chat protocol. kimi acp streams message chunks, tool calls, plans and permission requests (session/request_permission). It lists no thinking stream and no sub-agent nesting. Sessions can be listed, resumed and forked.
  • Sub-agents. An Agent tool runs sub-agents (types coder, explore, plan, and custom ones). Custom agents are Markdown files with frontmatter in .kimi-code/agents/ or .agents/agents/ in the project. Sub-agents cannot start further sub-agents. Each sub-agent writes its state to <session>/agents/<id>/wire.jsonl.
  • Models per agent. There is no model field in an agent file. The model is chosen when the Agent tool is called, from a "sub-agent model pool" of two or more models. So a Brain, Builder and Recall tiering is possible, but it is steered by the prompt, not fixed per file. The pool's exact setting is unverified.
  • Hooks. JSON arrives on stdin. Events include PreToolUse, PostToolUse, PermissionRequest, Stop, SubagentStart, SubagentStop, TaskStarted, SessionStart and SessionEnd. Only PreToolUse, Stop and UserPromptSubmit can block. The payload has the session id and working folder but, as documented, no transcript path and no agent id.
  • Where hooks live. Only in the user's ~/.kimi-code/config.toml or from plugins. There is no per-project hook file.
  • Project files. AGENTS.md (not CLAUDE.md), skills in .kimi-code/skills/ (same SKILL.md form as Claude, but it does not read .claude/skills), agents in .kimi-code/agents/. No documented project MCP file.

2. The three problems to solve

  1. Hooks are global, Foreman's rule is project-only. Foreman's setup rule (in CLAUDE.md) is that setup only writes project-level files and never changes global config. That rule is written for setup, so applying the same idea to hooks is my choice, not a settled rule. Kimi reads hooks only from the user's own config. Options, to be settled in the spike: launch each Kimi tile with KIMI_CODE_HOME pointing at a Foreman-managed folder that holds the hook entries (the sign-in would need to carry over, unverified); or skip hooks and build the graph from ACP plus the wire.jsonl files; or ship the hooks as a Kimi plugin. I will not edit your real ~/.kimi-code/config.toml.
  2. The graph and the council check read Claude files. The graph reads Claude hook events (core/claude-agents.ts, core/orchestration-graph.ts) and the stop check reads Claude's transcript. Kimi gives no transcript path. Because Foreman drives Kimi over ACP, Foreman itself sees every tool call, so the council check can run in Foreman instead of in a hook.
  3. The kit is Claude-shaped. It writes .claude/agents, .claude/skills and CLAUDE.md. For Kimi it must write .kimi-code/agents, .kimi-code/skills and AGENTS.md, from the same single source of rules.

3. What the code map says

  • OpenCode is terminal-only in Foreman: a plain opencode tile with no chat driver (core/launch.ts), and a test asserts chat cannot launch for it. The installer text in shared/install.ts still says "OpenCode terminals and chat", which is wrong. It gets fixed in phase A.
  • A search for 'opencode' hits about 35 source files, including renderer files such as TileFrame.tsx, the Terminals settings section and core/store.ts. Step A1 starts with the full list.
  • The installer already has a "main CLI" setting (MainCliKind in shared/install.ts) that makes Claude optional when OpenCode is the default. Kimi extends that same mechanism.
  • Claude's chat view reads Claude's own format (core/claude-chat-map.ts). MCP is already handled per command-line tool, so a Kimi MCP adapter follows OpenCode's pattern.
  • Foreman has an OpenCode sub-agent reader (listChildSessions in core/opencode.ts) that nothing calls outside its test, so OpenCode has no graph support today either.

Phase A: Kimi as a main agent, terminal tile

Phase B: the neutral event layer and the Kimi chat view

Phase C: graph and sub-agents on Kimi

Phase D: the Model Engine kit for Kimi

Phase E: finish

5. How you test it

  1. Install Kimi Code CLI, run kimi once and sign in with /login. I cannot do the sign-in for you.
  2. In Foreman set the main agent to Kimi for a project. With Claude uninstalled or not signed in, start a thread: it opens as a chat, not a terminal (after phase B).
  3. Switch Orchestration on and ask for a small edit. The graph lights Builder and Council, and the Agents panel lists the sub-agents (after phase C and D).
  4. Switch the setting back to Claude. Everything works as it does today.

6. Risks

  • The refactor is the danger, not Kimi. Moving the chat mapper and the graph onto a neutral format touches the code you use every day. The rule for phase B and C is that every existing test passes unchanged before and after, and the Claude behaviour is checked in the app.
  • Weaker model steering. Kimi has no per-agent model field, so the tiering depends on prompt wording. It may be less reliable than Claude's per-agent model.
  • Kimi moves fast. Version 2.5.1 came out the same day as this research. Pin the tested version in the installer row and note it.
  • Permissions. Foreman never passes --yolo or --auto by default.

7. Decisions for you (my pick first)

Order against the phone plan: the phone page reuses the desktop chat, prompt-card and graph components. Because phases B and C add an adapter and do not change those components, the two plans do not collide, and the phone plan can go first as listed in Next up. If a Kimi step ever has to change a component's inputs, the phone work must follow it.

  1. Order: spike, then phase A, then the neutral-event refactor (B and C) as its own step, then the kit (D). You can stop after A and still have Kimi tiles (my pick), or go straight to chat.
  2. Hooks: decided by the spike. My lean is a per-tile KIMI_CODE_HOME if sign-in carries over, otherwise ACP plus wire.jsonl. I will not touch your real Kimi config.
  3. Default agent: stays Claude. Kimi is chosen per project or in Settings (my pick).
  4. Sign-in: Kimi keeps its own login and Foreman stores no key (my pick).
  5. Auto-approve flags: never passed by default (my pick), or an off-by-default switch in Settings that you turn on yourself.
  6. Other ACP agents later: build the client generally so another agent that speaks ACP could plug in (my pick). I have not checked that Gemini CLI does.
