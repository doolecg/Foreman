Scheduled tasks

Status: plan only, nothing built. Builds after the run-scripts plan (plan-run-scripts-sat-2026-11-07.html), because a task can run one of those scripts. Branch: dev-4.4.0.

Read this first

  1. A scheduled task is a name, a time rule, a project and an action: send a prompt to Claude, run a project script, or both in that order.
  2. Version 1 runs tasks only while Foreman is open. The Windows Task Scheduler is not in version 1. A task that was due while Foreman was closed is marked "missed" and does not run by itself.
  3. An unattended agent is a risk. Scheduled prompts never run in Bypass mode, and anything that needs your approval waits and sends a notification.
  4. Section 6 has the choices for you. I have picked a default for each, so "go" is enough.

1. What you get

  • A "Scheduled" page (or tab) listing every task with its next run, last run, result and an on/off switch.
  • An editor: name, project, time rule, action, and an optional run limit per day.
  • Time rules: once at a date and time, every N minutes or hours, daily at a time, weekly on chosen days.
  • "Run now" on each task, for testing it without waiting.
  • Each run is kept as a normal thread in its project, named after the task, so you can open it and read what happened.

2. Where the data lives

Task definitions in one project file, .foreman/schedules.json (the same folder as run scripts, project-level files only). Note: .foreman/ is in this repo's .gitignore, so these files stay out of git here; decide in step 1 whether they should be shared. The last-run times and results live in Foreman's own app data, not in the project, so they never end up in git.

3. How it runs

  • A small timer in the main process wakes once a minute, finds the tasks that are due and starts them. It uses no tokens while idle.
  • One scheduled run at a time. A second due task waits in a queue.
  • A prompt task opens a new thread in the project and sends the prompt in plan or default mode, never Bypass. A script task uses the run-scripts runner and stops by PID.
  • The PC asleep or Foreman closed at the due time: the task is marked "missed" with the time it was due.
  • Each task has a daily run cap (default 3) so a bad rule cannot burn your token allowance.
  • A new task starts switched off. You turn it on after checking its time rule and cap.

5. How you test it

  1. Add a task "Test" in a project: every 1 minute, prompt "say hello".
  2. Wait a minute. A new thread named "Test" appears and Claude answers. Switch the task off and it stops.
  3. Close Foreman across a due time, then reopen it. The task shows "missed" and has not run.

6. Decisions for you (my pick first)

  1. When tasks run: only while Foreman is open (my pick), or also when it is closed through the Windows Task Scheduler (later, more work).
  2. What a task does: a prompt, a script, or both (my pick).
  3. A missed task: mark it missed and do nothing (my pick), or run it once when Foreman opens.
  4. Daily cap: 3 runs per task per day by default (my pick), or no cap.

7. Out of scope

  • Running when Foreman is closed or the PC is asleep.
  • Tasks that run on a trigger (a file change, a git push). Time rules only.
  • Running tasks on another machine.

8. Risks

  • Token cost. Every prompt task is a real Claude turn. The daily cap and the "off by default" switch limit it, and the editor shows the cap next to the time rule.
  • Unattended edits. A scheduled prompt can change files while you are away. Plan or default mode should make edits wait for approval, and the notification tells you. Step 1 confirms how a scheduled run behaves when nobody is there to approve.
  • Clock changes. Daylight-saving shifts are the usual bug in schedulers. Step 2 has tests for them.
