Foreman on your phone

Status: plan only, nothing built. Branch: dev-4.4.0. Design mockup: design-phone-ui.html (same folder). Code map done 5 November 2026.

Read this first

  1. Foreman serves its own screens to your phone's browser. You see your real projects, threads, graph and approvals, not a separate app.
  2. It reaches your PC over Tailscale (a private network between your devices). Nothing is opened to the public internet, ever.
  3. Your PC must be on and Foreman must be open. It is off until you switch it on in Settings > Phone access.
  4. This is the riskiest feature so far, because a phone that can approve things can make your PC run commands. Section 4 is the security design. I want your yes on section 7 before I build.

1. What you get

  • Open one address on your phone, pair it once with a QR code, and from then on it opens straight in.
  • Five phone screens, designed for one hand: projects and threads, the chat with a composer that sits above the keyboard, the Agents graph in one column, an approvals inbox, and the connect screen.
  • Big Approve and Deny buttons for permission, question and plan cards. Approving always takes a tap, never a swipe.
  • A "reconnecting" banner when the connection drops. Messages you type wait in a queue, and Approve is greyed out until it is back.
  • A desktop page, Settings > Phone access: the on/off switch, the pairing QR, the list of paired phones with a Forget button each, and "Forget all phones".

2. How it works (from the code map)

  • The desktop window talks to the main process through a table of handlers (foreman.handlers[channel] in main/ipc.ts). That table does not depend on Electron, so a WebSocket server can call it directly.
  • Chat calls need checking. The chat channels (chat:*) are not in the core channel list in shared/ipc.ts, and the desktop wrapper in main/ipc.ts also turns errors into a safe form and closes a tile on scratch:delete. Step 1 finds where the chat handlers are registered, and the phone server must reuse that error handling and not skip it. Step 1 also names the channel that starts a new thread, which the list in section 4 does not name yet.
  • Today the app refuses any page that is not the dev address or a file: page (main/guard.ts). The phone needs its own, separate trust rule tied to its token. The desktop rule stays as it is.
  • The phone page has no window.foreman, so a small shim sends the same calls and the same live updates over the socket. The screens keep using the code they use now.
  • The server serves the built renderer from out/renderer, with a phone layout switched on for narrow screens.

3. Tailscale in plain words

You install Tailscale on the PC and on the phone, signed in to the same account. Each gets a private address. Foreman listens only on the PC itself (127.0.0.1). You run one command, tailscale serve, which puts it on your private network with a proper HTTPS address. Foreman shows you that command and the address in Settings. Your PC never listens on your home network or the internet.

4. Security design

  • Off by default. Switching it on is a deliberate act in Settings, and it turns off again when Foreman closes.
  • Local only. The server binds to 127.0.0.1. It never binds to 0.0.0.0. Tailscale does the reaching.
  • Pairing. The desktop shows a QR with a one-time code that works for 5 minutes and once. The phone swaps it for a long random device token (32 bytes). The desktop keeps only a hash of it. Each phone has a name and can be forgotten on its own.
  • Checks on every connection. Token compared in constant time. The Host and Origin headers must be the Tailscale address you set, which stops a web page on another site from using the socket. A few wrong tries in a row lock pairing for a while.
  • An allow-list of channel names, not prefixes. Names like app:, shell: and browser: mix safe and dangerous calls, so the phone gets an explicit list. It covers listing and reading projects and threads, sending a chat message, answering a permission, question or plan card, interrupting a turn, and the graph.
  • Desktop only, never on the phone: shell and terminal writes, settings changes, opening paths or links, install and update, adding MCPs, setup and import, browser cookies and confirmations, picking folders, deleting projects.
  • No Bypass from the phone, checked by value. An allow-list of names cannot enforce this alone, because the mode call (chat:setMode) takes the mode as a value. The server refuses the Bypass value itself, and also refuses to start a thread in it. The phone may change between the other modes only if you say so in section 7.
  • Approval answers are checked by value too. A permission answer can mean "always allow", which writes a rule into the project's settings, or "approve and switch to accept-edits", which changes the thread's mode. The phone may only answer allow once or deny. The server refuses the other two answers.
  • The weak point is a stolen phone. Anyone holding an unlocked paired phone can approve things. The mitigations are the Forget button, a device list that shows the last time each phone connected, and a note in Settings telling you to keep the phone locked.

5. Steps (one at a time, each with a check)

6. How you test it

  1. Install Tailscale on the PC and on the phone and sign both in to the same account.
  2. In Foreman open Settings > Phone access, switch it on and run the tailscale serve command it shows.
  3. On the phone scan the QR. Open a thread, send "say hello", then trigger a permission card and tap Allow.
  4. Turn the phone's Wi-Fi off and on. The banner appears, then clears, and the queued message sends.
  5. In Settings press Forget on the phone. The phone drops to the connect screen.

7. Decisions for you (my pick first)

  1. HTTPS: use tailscale serve for a real HTTPS address (my pick), or plain HTTP on the private address. Plain HTTP works but blocks "add to home screen" and some phone features.
  2. Phone can start new threads: yes, in a project you already have (my pick), or it can only continue existing threads.
  3. Bypass from the phone: never (my pick). Other mode changes from the phone (Shift+Tab style): allowed between plan, default and accept-edits (my pick), or none.
  4. Tailscale: it is free for personal use and its apps are mostly open source, but the service is a company's. If that breaks your "free and open source" rule, the other route is a plain VPN you run yourself (WireGuard), which is more setup.

8. Out of scope for version 1

  • Push notifications to the phone (needs more than the browser gives on iPhone). The Inbox tab and its badge show what is waiting while the page is open.
  • Working while Foreman is closed or the PC is asleep.
  • Reaching Foreman over the public internet, or sharing it with anyone else.
  • The terminal view and the file and diff panels on the phone.

9. Design notes and not verified yet

  • The mockup reuses Foreman's own colour tokens (a neutral charcoal with an orange accent), so the phone matches the desktop app. The phone graph uses 15px sentence-case card names, not the desktop's small spaced capitals, because the UI rules ban those. Changing it back is one line.
  • Once you approve the mockup, the style gets saved to the design bank so later screens match it.

Not verified:

  • That a WebSocket passes cleanly through tailscale serve on your setup, and which Host header tailscale serve forwards. The Host and Origin check in section 4 depends on it, so step 3 tests both on a real phone before the check is fixed in code.
  • Where the thread sidebar lives in the code. The map did not find it, so step 6 starts by locating it.
  • The mockup was not rendered in a browser. The chat screen's message stack may clip at the top.
